microblaze: __moddi3 is wrong for almost every input

libgcc's MicroBlaze __moddi3 has been wrong since the port landed in 2010.
It returns the wrong answer for most inputs, differently on each byte order,
and for an LLONG_MIN dividend it either fails to terminate or returns
nonsense depending on the byte order.

These are two ways to fix it, and you should apply one or the other, not both.
Each applies to an unpatched master on its own; 2/2 is not a follow-on to 1/2.
Both touch libgcc only.

  1/2  Ramin Moussavi's fix to the existing assembly, with my additions.
  2/2  Delete the assembly and use the generic libgcc2.c version.

I measured them rather than guessing, and would rather you chose.

Which test proves it
--------------------

gcc.c-torture/execute/arith-rand-ll.c, which exercises __moddi3 through its
signed long long block over 10000 random bitstrings and checks
r1 * yy + r2 == xx.  On qemu-system-microblaze and qemu-system-microblazeel,
machine petalogix-s3adsp1800:

                      unpatched    with 1/2    with 2/2
  microblaze-elf        abort        pass        pass
  microblazeel-elf      abort        pass        pass

So the bug is provable with a test already in the tree, on both byte orders,
and no new test is needed to justify the fix.

Choosing between them
---------------------

2/2 is tempting because hand-writing this helper is close to unique.  Across
libgcc, ia64 is the only other target with a moddi3 in assembly, and its
reason does not transfer: lib1funcs.S builds it out of the FP divide sequence
from the Intel optimization guide, which is a hardware argument MicroBlaze
cannot make.  visium supplies a C version, pa rebuilds the generic one for a
32-bit word, and arm/symbian, avr, bpf and nds32-mculib exclude the helper
outright.  No other port hand-writes radix-2 soft division.  A routine almost
nobody felt the need to write by hand, and which was wrong for sixteen years,
is a reasonable thing to delete.

The measurements argue the other way, and the gap is a gap in algorithm rather
than in how tightly each is written.  The assembly is binary restoring
division, radix 2, one quotient bit an iteration -- Koren, Computer Arithmetic
Algorithms, section 3.2, which 1/2 cites in its header and whose notation its
comments use.  The generic path is Knuth's Algorithm D, TAOCP volume 2 section
4.3.1: digit recurrence at radix 2^16 with quotient-digit estimation and
add-back, reached through __udivmoddi4 and longlong.h's __udiv_qrnnd_c.  That
is why the two differ by tens of percent rather than a constant factor, and
why the figures below are not a like-for-like comparison of two codings of the
same method.

4701 vectors with expected values computed on the host, executed instructions
counted exactly with -icount 0, the generic version at -O2 since that is what
libgcc builds LIB2FUNCS at:

                       code size      executed insns
  assembly __moddi3        44      be 2777735  le 2777672
  generic C at -O2         62      be 3995016  le 3988505
    + __udivmoddi4     be 1030
                       le 1028
    total              be 1092       +43.8%      +43.6%
                       le 1090

About 25 times smaller and about 30% fewer instructions, some 258 a call.  On
an embedded target that is not close, so I recommend 1/2.  Two caveats in
fairness to 2/2.  __udivmoddi4 is shared, so a program already doing 64-bit
unsigned division links it anyway and the generic __moddi3 then costs 62
instructions rather than 1092.

And, more to the point, Xilinx already did 2/2.  In their GCC fork,
7090a49d007 of 2014-04-18 -- Nagaraju Mekala, "Removed moddi3 routinue" --
deletes the file with the message "Using the default moddi3 function as the
existing implementation has many bugs".  Its t-microblaze hunk is identical
to 2/2's.  It was never sent here, so upstream has carried for twelve more
years a routine the vendor had already written off, and both their 4.8.3 and
13.3.0 trees have been on the generic path since.  If you take 1/2, you are
reinstating something its own maintainer gave up on; that is defensible now
that it is correct and measured, but it should be a decision rather than an
oversight.

The two also disagree for x % 0, undefined either way.  The assembly returns
zero, matching divsi3.S, modsi3.S, udivsi3.S and umodsi3.S.  The generic
version returns the low word of the dividend, because libgcc2.c does
"d0 = 1 / d0" to provoke a hardware trap and on MicroBlaze that is a call to
__udivsi3, which itself returns zero for a zero divisor -- so no trap, and the
algorithm runs on with d0 still zero.  Neither matches a core with hardware
divide, where a % b is a - (a / b) * b and a zero quotient makes a % 0 give a;
that divergence predates this series and aligning it would touch all five
helpers.

What the existing test does not reach
-------------------------------------

arith-rand-ll.c catches the bug, but it would be misleading to let that stand
as evidence the routine is well covered.  Modelling the loop bit-exactly on
the host and counting the states each stream reaches:

                                   iterations   partial rem >= 2^63   |D| = 2^63
  arith-rand-ll.c                    331,380             0                0
  my own 4701-vector set             266,260             6               26

arith-rand-ll.c never drives the partial remainder across the sign boundary
and never divides by LLONG_MIN.  That matters because the loop's keep-or-skip
decision reads the sign bit of a 64-bit subtraction to settle an unsigned
comparison, and the sign boundary is where one would look for that to break.

It does not break, for a reason rather than by luck: D <= 2^63 since it is the
magnitude of a signed 64-bit value, and the loop keeps 0 <= R < D, so R' - D
lies in [-D, D-1] and is always in signed range, where the sign bit is the
sign of the true difference.  The same bound is why no 65th remainder bit is
needed.  1/2 states that where the comparison is.

Reaching the state needs both magnitudes within a hair of 2^63.  Sweeping that
region exhaustively -- 67,108,864 cases -- the signed test never disagrees with
a true unsigned compare, the invariant never breaks, no answer is wrong, and
the partial remainder reaches exactly 2^63 and never more.  All 8192 cases that
get there have the dividend exactly LLONG_MIN; on the target both fixes answer
all 8192 on both byte orders, and so does the generic C.

I have those vectors and can send a deterministic test for them separately if
that is wanted.  I am not proposing to add them to arith-rand-ll.c: it is built
on random bitstrings, so fixed corner values do not belong in it, and it is
shared by every target, which makes widening it a testsuite conversation
rather than a MicroBlaze one.

The wider point: the coverage that exists does catch this, so the reason a
routine this broken went unnoticed from 2010 to 2026 is that the execute
testsuite does not appear to be run for MicroBlaze at all.  Fixing __moddi3
does not fix that, and it is likely not the only thing hiding.

Provenance
----------

The assembly fix in 1/2 is Ramin Moussavi's, from OpenADK, and 1/2 credits him
in its first paragraph.  He has agreed to my submitting it; I sign it off
because the additions are mine and he is not sending it himself.

My additions reach the instruction stream, so here is what they cost:

                        code size      executed insns
  his patch as sent          56      be 3607673  le 3607610
  1/2 as sent here           44      be 2777735  le 2777672

Most of that is dropping the quotient.  His patch fixes the return value so
that r3:r4 is returned instead of r29:r30, which leaves the quotient in
r29:r30 computed and never read; taking it out removes four instructions from
the loop body, two from the setup and the four that spilled and reloaded it,
and lets the loop tail collapse to a single BNEi for an eleventh.  The rest are
an unreferenced label with the BRI that only jumped over it, and a delay slot
on the first zero test his version left empty.

Beyond the code: comments rewritten, registers and labels named after the
reference, the divide-by-zero note, the invariant above, and a correction to
his commit message -- it said big-endian got 30079 of 40420 values wrong while
little-endian hung, but which failure mode appears first depends on the order
of the vectors, since the routine both hangs and answers wrongly.
